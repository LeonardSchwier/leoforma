# Changelog

Versions follow [semver](https://semver.org). Release tags are `vMAJOR.MINOR.PATCH`.

## Unreleased

- Fixed: the `Dialog` and `Sheet` focus trap counted controls that CSS keeps from taking focus (`display: none`, `visibility: hidden`, the content of a closed `<details>`) as tab stops. When one was the first or last stop, Tab or Shift+Tab at the real edge was left to the browser, which could not focus it and moved on out of the modal (WCAG 2.4.3, reproduced in Chromium 157). The trap now asks `element.checkVisibility({ checkVisibilityCSS: true, visibilityProperty: true })` each time it needs the stops (when focus is placed on open and on every Tab), so a control the browser cannot focus is no longer a stop and nothing is cached. Opacity and `content-visibility: auto` are not passed, so a transparent control and an off-screen section are still stops. Content of a closed `<details>` is left out from the markup alone, so that holds in every engine, nested disclosures included. The `<summary>` of a `<details>` (its first `<summary>` child, the one a browser makes focusable) is now a stop. It was not before, so Tab wrapped past a trailing disclosure and left it unreachable from the keyboard, or, with controls inside it, left the dialog. Initial focus (without `initialFocusRef`) now skips a hidden first control, so it lands on the first one the user can reach; if every control is hidden the dialog surface takes focus, as it does for a dialog without controls. A browser without `checkVisibility` (Chrome before 105, Firefox before 106, Safari before 17.4) keeps the earlier answer for `display` and `visibility`: a control hidden only by CSS still counts, so mark it `hidden` or `inert` as well if that matters there. No props changed.
- Changed (breaking for a host that calls them directly; a minor version while below 1.0): the exported `focusableElements` returns fewer elements than before (those above) and now includes disclosure summaries, so it returns nothing for a `container` that is not rendered (detached, or under `display: none` or `visibility: hidden`) in a browser with `checkVisibility`. The exported `FOCUSABLE_SELECTOR` now also matches `details > summary:first-of-type`; a host that builds its own list with `querySelectorAll(FOCUSABLE_SELECTOR)` gets disclosure summaries too. The release that ships this one should be 0.3.0.
- Fixed: pressing Escape to hide a `Tooltip` that was showing inside a `Dialog` or `Sheet` closed the whole dialog instead, and with it anything the user had typed (WCAG 1.4.13, dismissible). The dialog listens for Escape in the capture phase and stops the event, so the tooltip's own listener never ran. A tooltip that is showing inside the dialog now takes the first Escape, whether keyboard focus or the pointer opened it, and the next Escape reaches the dialog, as for a `Menu`. The dialog consumes that Escape (`preventDefault` and `stopPropagation`), as it does for any Escape, and does so even with `closeOnEscape={false}`. A tooltip that is not showing (disabled, or never opened), or one left open on the page behind the modal, does not take it, and an Escape outside a dialog behaves as before. An Escape that an input method is composing with is still left alone. Internal registry in `src/components/tooltipRegistry.ts`, not exported; no props or exports changed.
- Added: `Menu` type-ahead, as the WAI-ARIA menu button pattern recommends. Typing characters moves focus to the next enabled item whose `label` starts with them: one letter steps through the items that share it and wraps (so does the same letter repeated), several different letters typed within 500 ms of each other match as a prefix (the current item counts, so "d" then "e" stays on "Delete"), and a pause or closing the menu starts a new search. Case and Unicode composition are ignored, independent of the browser's locale. Space joins a search under way only when some label continues with a space ("Save as"); otherwise it activates the focused item exactly as before, so "d" then Space activates the "Delete" it landed on. A Space the search took has its key-up cancelled, also when the next key went down before Space was released (fast typing), so it cannot click the item the search just focused. The menu consumes the characters it reads, matched or not (`preventDefault` and `stopPropagation`, as for Escape), so a host's bubbling single-key shortcut no longer also fires while a menu is open; a capture-phase listener still sees them and can check `defaultPrevented`. Ctrl, Alt and Meta chords and keys an input method is composing are not read; AltGr, which Windows reports as Ctrl and Alt together, is. No props changed.
- Changed (development only, nothing in the published package): the dev toolchain moves to vitest 5.1 and typescript-eslint 8.73, which clears the 2 critical (`tinypool`) and 7 moderate (`minimatch` and `@vitest/mocker` chains) advisories `npm audit` reported; only an unpatched `picomatch` ReDoS remained at the time (no fixed release existed yet). As of 2026-11-20 `npm audit` reports nothing: the advisory no longer applies to `picomatch` 4.0.7. Developing now needs Node 22.12 or newer (`engines.node` and CONTRIBUTING say so; CI already ran Node 22), and `tsconfig.json` lists the `node` types the tests use. The component API, tokens and built output are unchanged.
- Fixed: a `Tooltip` opened by keyboard focus closed 150 ms after the pointer hovered the trigger or the tooltip and left, although focus was still on the trigger, so a keyboard user who brushed the mouse lost the description (WCAG 1.4.13, persistent). A tooltip that focus opened now stays open while the trigger matches `:focus-visible`, whatever the pointer does, and closes on blur or Escape as before. `:focus-visible` is read when the pointer leaves, so a mouse click that merely focuses a button does not pin the tooltip open (it still closes 150 ms after the pointer leaves), while a click-focused trigger counts if the user has pressed a key on it before the pointer leaves. After Escape, a tooltip the pointer opens again closes as a hover tooltip does. A browser without `:focus-visible` keeps the previous behaviour. No props changed.
- Fixed: a `Tooltip` was not hoverable (WCAG 1.4.13): `.ds-tooltip` had `pointer-events: none` and the tooltip closed the moment the pointer left the trigger, so a low-vision user who magnifies the screen and moves the pointer onto the tooltip to read it made it vanish. The tooltip now takes pointer events, and when the pointer leaves the trigger or the tooltip an open tooltip waits 150 ms before closing, so the pointer can cross the gap and rest on it; coming back to either cancels the close. Escape and blur still close it at once, and a hover that has not yet shown (still inside `delay`) is cancelled at once as before. While open, the tooltip now covers what lies under it and takes the clicks meant for it. Keeping a tooltip that keyboard focus opened is the next entry. No props changed.
- Breaking (0.x, minor): a `Button` or `IconButton` with `loading` is no longer natively `disabled`. A focused button that becomes disabled loses focus (to the page body in Chromium; checked there), so a keyboard or screen reader user who pressed "Save" lost their place on every async action (WCAG 2.4.3). It now stays focusable and carries `aria-disabled="true"` and `aria-busy="true"`; the click is swallowed (`preventDefault`, so a submit or reset button does nothing, and `stopPropagation`, so an enclosing Card or row does not receive it, as before). An explicit `disabled` still sets native `disabled`. A host that asserts `button.disabled` while loading must assert `aria-disabled` instead, and CSS that targeted `button:disabled` for the loading look should target `[aria-busy="true"]`. The loading look is dimmed to 0.7 rather than the 0.5 of `:disabled`, because the focus ring is dimmed with the element and 0.5 would drop it below 3:1 on the light themes (WCAG 1.4.11; `test/contrast.test.ts` now computes it). In forced-colors mode a busy button is restated in `GrayText`. Do not pass `disabled` together with `loading` (for example `loading={saving} disabled={saving}`): `disabled` wins and the button then loses focus as before, while `loading` alone already blocks activation. Focus, key and pointer-up/down events, and capture-phase click listeners, are no longer suppressed while loading as they were by native `disabled`; only `onClick` is guarded.
- Fixed: `Tabs`, `SegmentedControl` and `Menu` treated an Alt, Ctrl or Meta chord on an arrow, Home or End key as a plain arrow, so Alt+Left (history back), Cmd+Down or a host shortcut both moved the widget's selection and was cancelled by `preventDefault`. These chords are now ignored, on the `Menu` trigger as well.
- Fixed: `Dialog` and `Sheet` closed on Escape, and wrapped focus on Tab, while an input method was composing (Japanese, Chinese or Korean text entry), where those keys cancel the composition or pick a candidate. A `Tooltip` was also dismissed by that Escape. Keys with `isComposing`, or `keyCode` 229 as Safari reports the key that ends a composition, are now left to the IME.
- Fixed: `Button`, `IconButton`, `Badge`, `Card`, `Input`, `Textarea`, `Select`, `Checkbox` and `Switch` silently dropped a host's `class` (Preact accepts `class` as well as `className`) because they set their own `class` after spreading the props. Both are now merged after the component's own classes.
- Fixed: a `ToastRegion` toast with a `duration` paused its timer on hover or focus through one shared flag, so a keyboard user focused on the Dismiss button who moved the mouse over the toast and away resumed the timer, and the toast auto-dismissed with focus still on it (WCAG 2.2.1). Hover and focus now hold the timer independently, and focus moving between controls inside the toast (a link in the message, then Dismiss) counts as staying focused.
- Fixed: opening a `Menu` did not move focus into it in Chromium, so a keyboard or screen reader user stayed on the trigger and the arrow keys did nothing. The menu renders `visibility: hidden` until it is measured and asked for focus in that same pass; browsers refuse `focus()` on a hidden element, jsdom does not, so the old tests passed. Focus now moves once the menu is visible, to the first enabled item (the last for ArrowUp). Re-positioning an open menu (a changed `align`) no longer pulls focus back to an edge item. The new tests emulate the browser rule.
- Fixed: in Windows High Contrast (`forced-colors: active`) a `Switch` was an empty pill whether on or off, a pressed toggle `IconButton` looked unpressed, every `Tabs` tab kept an underline so the selected one could not be told apart, and the selected `SegmentedControl` option differed only by font weight. `components.css` now restates each state in system colors (`Highlight`, `HighlightText`, `CanvasText`, `Canvas`). The pressed `IconButton` and selected `SegmentedControl` option opt out of `forced-color-adjust` (Chromium otherwise paints a Canvas backplate behind text on an author fill, which turns a white label into white on white) and restate their focus ring. Nothing changes outside forced-colors mode. `test/forcedColors.test.ts` requires a forced-colors rule for every state selector in the stylesheet.
- Fixed: `Tabs` and `SegmentedControl` put their single tab stop on the selected item even when it was disabled (or, for `SegmentedControl`, when the value matched nothing and the first option was disabled). A disabled button cannot take focus, so the whole group was unreachable by keyboard. The stop now falls back to the first enabled item and arrow keys start from it.
- Fixed: an open `Menu` stayed open, with nothing to dismiss it but Escape or a click elsewhere, when its `disabled` prop turned true or its `items` became empty. It now closes.
- Fixed: `Input`, `Textarea` and `Select` discarded a host's own `aria-invalid` when no `error` text was set. `error` still wins and forces `aria-invalid="true"`.
- Fixed: `IconButton` rendered `aria-pressed="false"` when `active` was not passed, so every icon button was announced as a toggle. `aria-pressed` is now only rendered when `active` is a boolean. A host that relied on the old attribute for a non-toggle button should pass `active={false}`, or better, drop it. A toggle that passes `active={maybeUndefined}` loses `aria-pressed` until the value is a boolean.
- Fixed: the `Dialog` and `Sheet` focus trap counted `tabindex="-1"` options (inactive `Tabs` and `SegmentedControl` items), hidden inputs and `hidden`, `inert` or `aria-hidden` subtrees as tab stops, so Tab could leave the dialog; Shift+Tab from the dialog surface could too.
- Fixed: Escape on an open `Menu` inside a `Dialog` or `Sheet` closed the whole dialog. The menu now closes first and the next Escape closes the dialog. `Menu` now stops the Escape event it handles, so a host's own `document` Escape listener no longer sees that press either. The dialog only defers to Leoforma's `Menu`, never to a foreign `role="menu"`.
