# Roadmap

Open work for Leoforma, derived from code review and consumer requests (the Leotheca and Leoposta roadmaps name no missing token, component or icon as of 2026-11-21). Items are ordered by impact. Each needs a test, and a component change needs an axe check (see [CONTRIBUTING.md](CONTRIBUTING.md)).

## Open

- [ ] **ToastRegion announcements.** Each toast carries `role="status"` or `role="alert"` and is inserted with its content, which some screen readers do not announce; the region itself is a plain landmark. Check with real assistive technology, then consider a pre-existing live region. If one is added: always-mounted polite and assertive containers inside the region with the toasts rendered into them, and `aria-atomic="false"` plus `aria-relevant="additions text"` on them (both roles imply `aria-atomic="true"`, so each new toast would re-announce the others), and the layout still needs checking. Reviewed 2026-11-20 and left open on purpose: its own gate, the assistive technology check, cannot be done without a device, and jsdom cannot show what gets announced.

## Done

- [x] **Dialog and Sheet focus trap counts CSS-hidden controls as tab stops** (2026-11-21): `focusableElements` (`src/components/overlayStack.ts`) now also drops elements for which `element.checkVisibility({ checkVisibilityCSS: true, visibilityProperty: true })` is false, feature-detected at call time and read on every call (nothing cached), so a `display: none` or `visibility: hidden` control is no longer the first or last "stop" and Tab or Shift+Tab at the real edge wraps instead of leaving the modal (WCAG 2.4.3). Opacity and `content-visibility` are not passed, so transparent and off-screen controls stay stops. Caveats from the 2026-11-20 review, all handled: `details > summary:first-of-type` joined `FOCUSABLE_SELECTOR` (the disclosure is reachable by Tab); content of a closed `<details>` is excluded from the markup alone (`insideClosedDetails`, no `checkVisibility` needed, nested disclosures included, which an engine without `checkVisibility` would otherwise count as a ghost last stop); when every stop is filtered the surface takes focus (existing path, now tested); initial focus skips a hidden first control (a gain, in the changelog). Decisions: no `getComputedStyle` fallback for engines without `checkVisibility` (Baseline since March 2024; a fallback is a second code path that still misses `content-visibility` and `display: contents`; both judges agreed, as does the existing `:focus-visible` pattern in `Tooltip`); a minor-version "Changed (breaking for direct callers)" changelog line, because `focusableElements` and `FOCUSABLE_SELECTOR` are exported, no version bump here. Real engine: before the change, in Chromium 157 (Playwright, a throwaway harness bundling the `Dialog` from `src`, not committed), Tab from the last visible control left the dialog when a `display: none` control followed it, initial focus failed to land when a `visibility: hidden` one came first, and Tab from a closed disclosure's summary left the dialog; after the change focus stayed inside in all of those, in a `visibility: visible` child of a hidden parent, in nested closed `<details>` with and without `checkVisibility` (deleted from the prototype to emulate an old engine). An independent run in Chrome 153 agreed. Tests: 20 new in `test/components.test.tsx` ("Dialog focus trap and CSS-hidden controls", "...in an engine without checkVisibility"), plus the stand-in `test/checkVisibility.ts` (jsdom has no `checkVisibility`; it models `display: none`, `display: contents`, `visibility`, closed `<details>`, and was compared with Chrome 153 by a judge); mutations (original source, no CSS check, no summary selector, `checkOpacity` passed, no feature detection, no `visibility` options, structural details check removed, summary of a closed `<details>` treated as hidden, stub without `display: contents`) each fail a matching test; `:first-of-type` is an equivalent mutant, because a non-main `<summary>` already has a negative `tabIndex`. Two independent reviews (opus, sonnet) found no Critical or High issues; their Medium and Low points (ghost summary stop without `checkVisibility`, undocumented `FOCUSABLE_SELECTOR` and empty-result change, broken docs sentence, dangling ROADMAP pointer, `display: contents` in the stand-in, missing stale-cache and opened-details tests) are fixed. `npm run check` passes with 446 tests (baseline 426). Unreleased, see the changelog (next release should be 0.3.0). Known limits: jsdom plus Chromium only; Firefox and WebKit were not run (no download access), so the `summary.tabIndex` of 0 for a main summary is taken from the HTML spec there; not tried with real assistive technology.
- [x] **Dev toolchain advisory: picomatch** (resolved 2026-11-20, no code change): the open item expected a patched `picomatch` release; none was needed. `npm audit` now reports `found 0 vulnerabilities` (it did flag a `lodash@4.17.15` probe in a scratch project, so the audit endpoint is working), the registry's bulk advisory endpoint returns `{}` for `picomatch` 4.0.7 and 4.0.6, `npm ls picomatch` shows 4.0.7 everywhere, and `npm view picomatch dist-tags` is still `latest: 4.0.7`. The advisory the item named no longer applies to the versions in the lockfile. If it is re-issued, `npm audit` will say so again and this should be reopened.
- [x] **Escape hides a showing Tooltip before it closes the Dialog** (2026-11-20): a `Tooltip` showing inside a `Dialog` or `Sheet` takes the first Escape and the dialog the next, so a keyboard user who only meant to hide a tooltip no longer closes the dialog and loses what they typed (WCAG 1.4.13, dismissible). Cause: the dialog stops Escape in the capture phase, so the tooltip's bubble-phase listener never ran. A tooltip registers in an internal registry (`src/components/tooltipRegistry.ts`, not exported) in a layout effect while `open && active`, and the dialog's Escape branch, after the Menu check, dismisses those whose anchor is inside its surface and consumes the key. Decisions: two judges (opus, sonnet) ranked this above the CSS-hidden tab stops and the toast live region; opus preferred a registry, sonnet a window-capture Tooltip listener, the registry was taken because it changes nothing outside a dialog and adds no public name. Tests: 11 new in the "Tooltip inside Dialog" block of `test/components.test.tsx` (focus-opened, hover-opened with focus elsewhere, Sheet, `closeOnEscape={false}`, nothing showing, a tooltip disabled while open, a tooltip left open behind the dialog, two stacked dialogs, IME composition, Escape outside a dialog unchanged, axe); the first four fail without the Dialog change, and mutations (every showing tooltip dismissed regardless of container, registered while not showing, Escape not consumed) each fail a matching test. An independent review found no Critical or High issues; its Medium (a passive effect left the registry stale for a frame) is fixed with a layout effect. `npm run check` passes with 426 tests (baseline 415). Unreleased, see the changelog. Known limit: jsdom only, not tried in a real browser or with assistive technology.
- [x] **Menu typeahead** (2026-11-19): typing characters in an open `Menu` moves focus to the next enabled item whose label starts with them (one letter cycles and wraps, several within 500 ms of each other match a prefix, a pause or closing resets). Space joins a search under way only when a label continues with a space, otherwise it activates as before; a Space the search took has its key-up cancelled even when another key went down first. The menu consumes the characters it reads, so a host's bubbling single-key shortcut does not also fire. Ctrl, Alt and Meta chords and IME composition are not read; AltGr (Ctrl+Alt with `AltGraph`) is. The search is a pure function (`src/components/typeahead.ts`, `findTypeaheadMatch`). Tests: 41 new (10 in `test/typeahead.test.ts`, 30 in the "Menu typeahead" block and 1 in "Menu inside Dialog" of `test/components.test.tsx`, incl. an axe check); they failed before the change, and 12 mutations (no key-up cancel, key-up flag cleared by any keydown, no AltGr, Ctrl+Alt read without AltGraph, disabled items included, no `stopPropagation`, no reset on close, Space consumed without a match, no repeat handling, stale flag kept, window anchored to the first key, `<=` at 500 ms, label read from DOM text) each fail a matching test. Two independent reviews (opus, sonnet) found one High (the key-up flag cleared by a rolled-over keydown, could click the wrong item in Firefox), a Space-after-match regression and a locale-dependent case fold; all three are fixed and tested. `npm run check` passes with 415 tests (baseline 374). Unreleased, see the changelog. Known limit: not tried with real assistive technology or in Firefox and Safari, only in jsdom.
- [x] **Dev toolchain advisories** (2026-11-18): vitest 3 to 5.1 and typescript-eslint 8.46 to 8.73 (`npm audit` went from 14 entries, 2 critical, 5 high and 7 moderate, to 11 entries, all high and all the one `picomatch` advisory above, so 0 critical and 0 moderate; the high count rose from 5 because typescript-eslint's chain now lists it too). vitest 5 needs Node 22.12 or newer, so `engines.node` and CONTRIBUTING say so (CI already runs Node 22), and `tsconfig.json` now lists the `node` types the tests always used (vitest no longer pulls them in). Test suite unchanged: 5 files, 374 tests before and after; `npm run check` green. Unreleased, see the changelog.
- [x] **Tooltip: a focus-opened tooltip stays open after hover ends** (2026-11-18): a `Tooltip` that keyboard focus opened no longer closes when the pointer hovers the trigger or tooltip and leaves (WCAG 1.4.13, persistent). It stays while the trigger matches `:focus-visible`, read when the pointer leaves so a mouse click that only focuses the trigger does not pin it open; blur and Escape still close it, and after Escape a pointer-opened tooltip closes as a hover tooltip does. Tests: 9 new in `test/components.test.tsx` (3 fail without the fix, verified by stashing the source change; the other 6 guard blur, Escape, click-focus, unrelated focus and a browser that cannot evaluate `:focus-visible`); jsdom answers `:focus-visible` like `:focus`, so the tests stub it. `npm run check` passes with 374 tests (baseline 365). An independent review found no Critical or High issues; its two wording and flag-reset points are applied. Unreleased, see the changelog.
- [x] **Tooltip is hoverable** (2026-11-17): `.ds-tooltip` takes pointer events and an open tooltip survives a 150 ms grace period after the pointer leaves the trigger or the tooltip (WCAG 1.4.13, hoverable). Escape, blur and focus behaviour unchanged. Tests: 10 new (9 in `test/components.test.tsx`, 1 in `test/tooltipStyles.test.ts`), 8 of which fail without the fix (verified by stashing the source change); `npm run check` passes with 365 tests (baseline 355). The persistent part of 1.4.13 for a focus-opened tooltip is split off as an open item. Unreleased, see the changelog.
- [x] **Loading buttons keep focus** (2026-11-16): `Button` and `IconButton` with `loading` stay focusable (`aria-disabled`, not `disabled`). Unreleased, see the changelog.
